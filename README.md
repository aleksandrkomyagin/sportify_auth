## 🚀 Описание

`sportify-auth` отвечает за:

- регистрацию и аутентификацию пользователей;
- управление токенами (JWT, ротация ключей, отозванные токены);
- активацию, деактивацию и удаление аккаунтов;
- Реализован паттерн Transactional Outbox. 
Раз в минуту запускается задача по расписанию, которая ходит в таблицу с событиями
и отправляет их в кафку

## 🧩 Архитектура

### Регистрация пользователя (2 этапа)

1. **Ввод номера телефона**
   - Проверяется уникальность.
   - Создаётся доменная сущность пользователя.
   - Сохраняется в Redis с TTL.
   - Kafka-продюсер отправляет событие → сервис уведомлений шлёт СМС с кодом.

2. **Подтверждение кода**
   - Код валидируется.
   - Из Redis достаётся сущность.
   - Создаётся пользователь.
   - Kafka-продюсер отправляет событие → микросервисы создают пользователя у себя.
   - Отдаётся JWT-пара: `access_token` и `refresh_token`.

### Аутентификация

1. **Ввод номера телефона**
   - Номер валидируется.
   - Kafka-продюсер отправляет событие → сервис уведомлений шлёт СМС с кодом.

2. **Подтверждение кода**
   - Код валидируется.
   - Отдаётся JWT-пара: `access_token` и `refresh_token`.

## 📱 Сессии на нескольких устройствах

**Sportify** поддерживает работу пользователя сразу на нескольких устройствах (например, смартфон и планшет).

При входе в систему создаётся новая сессия, привязанная к refresh-токену.

Информация о новой сессии публикуется в Kafka-топик `new_session`, чтобы остальные микросервисы синхронизировали состояние пользователя.

При выходе или отзыве токена публикуется событие в Kafka-топик `delete_session`.

Таким образом:

Один пользователь может быть одновременно авторизован на нескольких устройствах.

Управление сессиями централизовано: выход из устройства автоматически делает refresh-токен и связанную с ним сессию недействительными.

Сервисы-читатели Kafka (new_session / delete_session) могут, например, уведомлять устройства или очищать кеш.

## 📱 Поддержка нескольких аккаунтов на одном устройстве

**Sportify** позволяет на одном устройстве одновременно иметь несколько аккаунтов пользователя:

Каждому аккаунту создаётся отдельная сессия с уникальным refresh-токеном.

Пользователь может быстро переключаться между аккаунтами без необходимости повторного входа.

При выходе из одного аккаунта его сессия становится недействительной, другие аккаунты продолжают работать.

События создания и удаления сессий публикуются в Kafka-топики `new_session` и `delete_session`, чтобы синхронизировать состояние аккаунтов между микросервисами.

## 🧠 Сервисы

- `UserService` — управление пользователями: регистрация, подтверждение, удаление, активация, деактивация.
- `TokenService` — генерация JWT, JWKs, обновление и отзыв токенов.
- `SessionService` — управление сессиями пользователя.
- `ConfirmationCodeService` — генерация, валидация и работа с кодами подтверждения (в отдельной Redis-базе).
- `KafkaProducer` и `KafkaConsumer` — взаимодействие с топиками (`notify_user`, `user_created` и др.).

---

## 🗃️ Redis (4 логические базы)

| №   | Назначение                     |
|-----|--------------------------------|
| 0   | Пользовательские операции      |
| 1   | Коды подтверждения (TTL)       |
| 2   | JWKS (RSA ключи)               |
| 3   | Отозванные токены              |

---

## 🔐 Безопасность

- Подпись токенов на RSA.
- JWKS с ротацией.
- Отзыв токенов.
- Проверка `iss`, `jti`, `type`, `exp`.
###
Ротация делается вручную, по запросу на определенный эндпоинт. При ротации, старый JWKS не удаляется.
За удаление JWKS отвечает отдельная задача.

---

## 🌀 Kafka

**Топики:**

- `notify_user` — отправка уведомления через внешний сервис.
- `create_user` — синхронизация пользователя между микросервисами при регистрации.
- `delete_user` — синхронизация пользователя между микросервисами при удалении.
- `update_user` — синхронизация пользователя между микросервисами при обновлении.
- `activate_user` — синхронизация пользователя между микросервисами при активации.
- `deactivate_user` — синхронизация пользователя между микросервисами при деактивации.
- `revoke_token` — синхронизация отозванных токенов между микросервисами.
- `new_session и delete_session` — синхронизация пользовательских сессий на разных мобильных устройствах между микросервисами.

---


## 🔁 Токены

- `access_token`: TTL = 10 минут
- `refresh_token`: TTL = 1 день
- При обновлении refresh токена:
  - Создаются новые токены
  - Обновленный токен становится недействительным

## 🔐 Аутентификация для межсервисных запросов

Часть запросов от других микросервисов к этому API **должны содержать сервисный JWT-токен** в заголовке `Authorization`.  
Без токена или с недействительным токеном запрос будет отклонён с ошибкой **401 Unauthorized**. Токен действительный 10 минут.

---

### Получение токена

1. Микросервис регистрируется в сервисе аутентификации (**Sportify M2M Auth Service**).
2. Для получения токена выполните запрос:

```http
POST https://m2m_auth.sportify.ru/auth/token
Content-Type: application/json

{
    "client_id": "my-service",
    "timestamp": 0,
    "signature: "signature"
}
```

### Права доступа (Scopes)
Внутри токена может содержаться список разрешений (scopes).
API будет проверять наличие необходимых разрешений для конкретного эндпоинта.

#### Пример payload токена:

```json
{
    "iss": "m2m-auth-service",
    "sub": "client_id",
    "scopes": {"read":["service_name", "service_name"], "write":["service_name", "service_name"]},
    "exp": 0
}
```
